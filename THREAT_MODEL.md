# django-auditlog threat model

## Overview

A Django extension records registered model lifecycle changes through signals, optionally attributes them to request users with middleware, and exposes historical rows through ORM helpers and Django admin. This fork writes auditlog_logentry_historical and routes new entries using instance._state.db, not the signal using alias (src/auditlog/registry.py:41; src/auditlog/models.py:58; src/auditlog/models.py:189). It runs inside the caller process rather than as a standalone authentication or audit service.

The normal integration installs the package into a Django application, registers selected models and optionally installs its middleware and admin. The caller still owns authentication, model access, database credentials, transaction boundaries and the audience for history. Logging a mutation does not authorize it. This model concerns the public library and generic integration duties; no particular production application, tenant layout or edge configuration is assumed.

## Threat Model, Trust Boundaries, and Assumptions

**Protected assets.** Old/new field values, object representations, additional_data, actor IDs and remote addresses stored in audit rows (src/auditlog/models.py:175). Audit provenance and retention; model/database authority remains that of the caller connection (src/auditlog/models.py:58). Related-row lifecycle is explicit: deleting an actor user sets actor to NULL, losing its stored identity link; deleting the referenced ContentType cascades to its audit rows. Retention procedures must account for both and preserve independent identity/records where required (src/auditlog/models.py:171; src/auditlog/models.py:177). AuditlogHistoryField is also a GenericRelation to LogEntry: when installed on an audited model, normal Django collector deletion can cascade through this reverse relation and remove prior history, independently of purge authority or key reuse; the registered post_delete capture subsequently creates the deletion record. Omit or decouple that cascading relation where history must survive object deletion, and use authorized explicit history queries instead (src/auditlog/models.py:308-333; src/auditlog/registry.py:46; src/auditlog/receivers.py:55-70).

**Actors and starting authority.** A host user may influence editable model fields and request headers, but is not thereby entitled to register models, control Django settings or read audit storage. An operator with management-command/database access can purge history; that is existing operator authority, not an end-user capability (src/auditlog/management/commands/auditlogflush.py:9).

**Trust boundaries and owned controls.**

- Application model save/delete signals cross into historical persistence; register chooses classes, include/exclude fields and custom handlers. Update comparison reads sender.objects by primary key; logging is not authorization of the original mutation (src/auditlog/registry.py:53; src/auditlog/receivers.py:36). Old-state lookup does not bind instance._state.db or the signal using argument: host manager/router selection can miss the key and suppress logging, or select a different row and produce a false diff. Align snapshot lookup with the audited write database (src/auditlog/receivers.py:28; src/auditlog/receivers.py:38). Update logging is registered on pre_save and inserts evidence before the model write. If the later write fails outside a shared transaction, a phantom audit row can remain. When evidence must describe only committed changes, require an atomic transaction covering audit and model writes on the same database; separately routed writes do not share that guarantee (src/auditlog/registry.py:44; src/auditlog/receivers.py:48). log_update ignores update_fields and compares all configured fields, so save(update_fields=...) can report in-memory changes that were never persisted. Restrict update diffs to fields written by the save when accurate evidence is required (src/auditlog/receivers.py:28; src/auditlog/receivers.py:44; src/auditlog/diff.py:116). An explicit save(using="B") of an instance loaded from A can emit pre_save while _state.db still names A. Because receivers ignore using and the manager selects _state.db, evidence can be inserted on A while the model write occurs on B; atomic(using="B") alone cannot cover that audit insert. Bind both snapshot lookup and audit insertion to the signal write alias before relying on same-database atomicity (src/auditlog/receivers.py:28-52; src/auditlog/models.py:59-60).
- Middleware consumes an authenticated request.user from caller authentication; first X-Forwarded-For value overrides REMOTE_ADDR. A threading.local slot gates globally connected signal receivers, and response/exception hooks disconnect using that slot. This assumes request contexts do not interleave on one thread: if they do, another request can overwrite the dispatch identity/address, causing wrong or missing attribution and cleanup of the wrong receiver. Use async-safe request-local context or exclude unsupported interleaving; a particular Django/ASGI adapter’s scheduling is not established here. Trusted proxy normalization belongs to the host (src/auditlog/middleware.py:20; src/auditlog/middleware.py:35; src/auditlog/middleware.py:45; src/auditlog/middleware.py:53; src/auditlog/middleware.py:73).
- JSON text is generated from diffs and parsed for display. Admin uses format_html for cells; password masking in msg is presentation-only, whereas diff persistence retains included values (src/auditlog/receivers.py:24; src/auditlog/diff.py:150; src/auditlog/mixins.py:65).
- Django admin registration inherits host site permissions; related-object query helpers filter identity, not user/tenant entitlement. Library users must authorize history readers separately (src/auditlog/admin.py:7; src/auditlog/models.py:63).
- CREATE capture removes prior audit rows for a reused content type/primary key using the current LogEntry manager before insertion. Cleanup routing is therefore separate from the explicit instance-database insertion; host multi-database and retention expectations must cover both (src/auditlog/models.py:51; src/auditlog/models.py:58). A lower-privilege creator allowed to reuse a historical primary key can thereby erase earlier matching history without purge authority. If retention is required, prevent caller-controlled key reuse or remove/separate this cleanup under retention authority (src/auditlog/models.py:53).

**Security objectives.** Keep log readers authorized for the full historical values, including data omitted from current records. Preserve actor isolation and treat forwarded addresses as provenance metadata rather than authenticated identity. Choose capture exclusions before persistence and define retention independently from admin presentation.

**Assumptions and unresolved controls.**

- Signal coverage depends on host mutation paths and registry flags; do not infer complete coverage of bulk SQL or independent writers (src/auditlog/registry.py:134). Registered M2M clear() is also omitted because post_clear supplies no truthy pk_set; provide explicit clear capture if the completeness requirement includes relation removal (src/auditlog/receivers.py:74). Other post-action M2M query, representation/serialization or audit-insert errors are caught by a blanket except and only logged. A relation mutation can therefore commit without complete evidence; a backend error that marks an enclosing transaction for rollback may instead prevent commit, so swallowed errors do not guarantee success. Monitor capture errors and use a stricter atomic capture path where completeness is required (src/auditlog/receivers.py:74-111).
- Packaging names django-auditlog 0.4.5; no release workflow appears in the supplied tree, so publisher access is unknown (setup.py:3).
- Host DB routers, historical-data retention, permitted audit readers and required mutation coverage remain unresolved. No append-only database control or automatic protection of backups is established by this library.

## Severity Calibration (Critical, High, Medium, Low)

| Level | Repository-specific example | Counterexample or limiting prerequisite |
| --- | --- | --- |
| Critical | A demonstrated history-access failure exposes a large, highly sensitive dataset or reusable privileged credentials. | Requires actual captured contents, reader reachability and broad impact; a logging package alone does not establish it. |
| High | A lower-privilege reader gains another user’s sensitive historical records or a meaningful secret. | Authorized administrators reading their intended audit data are expected recipients. |
| Medium | A reachable attribution or capture failure materially defeats a defined accountability requirement. | A spoofed address with correctly bound actor and no downstream reliance may have much less impact. |
| Low | Limited metadata disclosure or a localized display/diagnostic defect without confidential values or authority gain. | Intentional operator purge and configured exclusions are not vulnerabilities by themselves. |
